# Root Cause Analysis: "Invalid category ID" Error

## Executive Summary

**Error**: Job posting fails with "Invalid category ID" error
**Root Cause**: Frontend uses hardcoded string identifiers (`'plumbing'`, `'electrical'`) while backend expects database-generated CUID identifiers (`'cmh9ksove000eiudfazei7qim'`)
**Severity**: CRITICAL - Blocks all job creation functionality
**Impact**: 100% of job posting attempts fail

## Root Cause Statement

**The frontend uses static, human-readable category identifiers (`'plumbing'`, `'electrical'`) hardcoded in `frontend/src/lib/utils.ts`, while the backend and database expect dynamic CUID identifiers generated by Prisma (`'cmh9ksove000eiudfazei7qim'`).**

When a user selects a category, the frontend sends the hardcoded string ID to the backend, which fails the database lookup in `validateCategory()` because no category exists with ID `'plumbing'` - only categories with CUID identifiers exist.

---

## Contributing Factors

### 1. **Architectural Mismatch**
- Frontend designed with assumption of static category IDs
- Backend designed with dynamic database-generated IDs
- No synchronization mechanism between systems

### 2. **Missing Category Fetch Logic**
- Frontend never fetches categories from backend API (`GET /categories`)
- Categories service exists but is unused by frontend:
  ```typescript
  // backend/src/modules/categories/categories.controller.ts
  @Get()
  async findAll() {
    return this.categoriesService.findAll();  // ✅ Available but not called
  }
  ```

### 3. **Incomplete DTO Validation**
- DTO only validates string type, not actual category existence
- Should use custom validator to check category ID before job creation
- No TypeScript type safety between frontend and backend category structures

### 4. **Development Workflow Gap**
- Database seeding creates categories with CUIDs
- Frontend development used placeholder IDs
- No integration testing caught the mismatch
